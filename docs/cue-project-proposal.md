# Cue 项目书

> 面向并行 AI 工作的会话注意力队列。
>
> 各处的 agent 继续工作，Cue 把需要你处理的会话送到面前。

版本：0.1 · 日期：2026-09-12 · 状态：产品与实施提案，尚未实施

## 1. 项目定位

Cue 捕获用户在本地和远程机器上运行的主流 coding harness session，持续接收会话变化，将需要人介入的会话组织成可逐项处理的注意力队列。

用户在 Cue 中查看新增消息与必要上下文、延后处理、标记已处理；存在现成、稳定维护且经过验证的发送实现时，提供快捷回复。否则，提供尽可能精确的原会话打开入口。

Cue 的基本对象是 session。消息是 session 的内容；一次新的问题、结果或审批形成待处理事项。界面默认每个 session 一张卡片，卡片内部可以有多个尚未处理的事项。

产品承诺：**集中发现需要你处理的会话，让你以尽量少的切换完成处理。**

## 2. 目标用户与问题

首批用户是同时使用多个 AI 编程会话的个人开发者：在终端、IDE、本地与远程机器之间切换，通常同时推进多个项目或工作分支。

现有工作方式的主要成本：

- 不断查看窗口，确认哪个 agent 已结束、报错或在等待回答。
- 新结果散落在多个入口，重要问题容易被普通进度消息淹没。
- 切回会话后，需要重新阅读上下文才能决定下一步。
- 在一个入口已处理的事项，另一个入口仍然提醒。

Cue 首先优化人的发现、判断与回应时间。产品价值不以 agent 数量或采集的消息总量衡量。

## 3. 与 TopCard 的关系

| 维度 | TopCard：当前项目 | Cue：新项目 |
|---|---|---|
| 定位 | 统一会话工作台 | 会话注意力队列 |
| 核心承诺 | 接入的会话在同一页面完成交互闭环 | 各处会话的待处理变化集中可见 |
| 接入方式 | 集成 harness 的运行与交互能力 | 观察已有 session，按实际能力提供操作 |
| 回复能力 | 完整接入的基础能力 | 有稳定开源实现才接入，否则快捷打开 |
| 日常入口 | 用户在工作台处理会话 | 用户继续在原环境工作，Cue 提供集中处理入口 |
| 首要工程要求 | 操作、运行状态与结果一致 | 采集完整、事项去重、投递结果明确 |

两者共享“让并行工作的 agent，有序地获得人的注意力”的设计理念。独立迭代，避免 Cue 被完整 harness 控制、模型配置和运行管理拖重。

TopCard 的统一处理承诺限定于已接入且通过验证的环境。Cue 不把观察到一个 session 等同于拥有它的输入或执行控制权。

## 4. 设计原则

### 4.1 注意力是队列的资源

中心区域一次聚焦一个 session。其他等待事项有明确次序，工作中的会话放在辅助区域。只有值得处理的变化进入注意力队列。

新事项出现时更新队列，不抢走用户正在阅读或输入的卡片；用户主动切换后，再按当前顺序进入下一项。

### 4.2 卡片承载会话，事项决定是否需要处理

一个 session 可有多次待处理变化。处理当前事项后，该 session 后续出现新的问题，可以重新进入队列。

查看、已读、延后、已处理与项目完成分别记录。agent 一轮结束也不等于用户任务完成。

### 4.3 原有工作习惯继续成立

观察接入默认不要求用户改变启动命令，不更改原会话文件，不强制注入提示词或安装模型侧工具。

如某条成熟的发送通道需要额外配置，作为该会话的可选增强接入。缺少它不影响收取与查看。

### 4.4 能力可见，结果可信

只显示当前来源实际支持的操作。快捷打开明确区分“定位原会话”“恢复已退出会话”“打开应用或目录”。不能精确定位时不标注为已打开原会话。

回复区分待投递、已确认接收、结果不确定与失败。点击发送不直接等于 agent 已开始工作。

### 4.5 安静优先

进度增量不反复通知。历史导入不触发新消息通知。对同一事项跨刷新、重连、重启去重；用户已经在来源端处理过的事项，有明确证据时同步关闭。

### 4.6 本地优先

首版本机保存索引与队列，不依赖云账户。远程来源通过用户配置的 SSH 通道接入。采集范围可查看、排除和暂停；不上传到第三方服务。

## 5. 核心用户旅程

1. 用户在原终端或 IDE 中照常启动 agent。
2. Cue 发现 session，展示 harness、机器、项目、最近活动和当前可用操作。
3. 新问题、审批、明确失败或一轮新结果出现，session 进入待处理队列。
4. 用户看到“为什么需要我”和上次处理之后的新内容，可展开完整已采集历史。
5. 用户直接回复，或者点击打开来源。普通回复与审批分开处理。
6. 获得发送确认或来源端新输入等明确证据后，更新对应事项；打开来源本身不算处理完成。
7. 用户处理下一张卡，原 session 后续有新事项时再次入队。

没有稳定回复能力的来源仍然完成第 1–4 步，通过打开来源完成第 5 步。

## 6. 界面与队列规则

### 6.1 页面结构

- 待处理队列：等待回答、审批、结果查看及错误处理的 session。
- 中心卡片：事项原因、来源、新增内容、必要上下文和当前操作。
- 工作区：正在运行或近期活跃的 session，不与待处理事项争抢中心位置。
- 历史入口：已处理、延后、静音以及历史会话，可搜索。

卡片保留折叠的工具结果与可展开消息；首屏突出“这次发生了什么”。复杂编辑、终端控制和深度调试继续交给来源界面。

### 6.2 首版排序

优先提供可解释的规则：手动置顶优先；其后按事项优先级和等待时间排序。默认区分明确等待人输入、错误、新结果三类，允许用户调整会话优先级。

延后事项在指定时间重新出现。普通流式输出不会反复重置等待时间；相同 session 的新增内容聚合到当前事项或生成有明确边界的新事项。

模型语义标签与自动紧急程度判断不作为首版依赖。原生事件足够时直接使用；状态没有可靠证据时显示未知，不靠“几秒没输出”伪造等待状态。

### 6.3 快速处理

首版动作：下一项、上一项、标记已处理、延后、置顶、打开来源；有能力时增加快捷回复。

输入中保留草稿；队列刷新保持卡片位置与滚动位置。完成处理后聚焦下一项。关键动作同时提供按钮和快捷键，快捷键避免覆盖输入框常规编辑行为。

## 7. 首版范围

### 必须交付

- 以 Claude Code CLI、Codex CLI 两类来源为首批验证对象。
- macOS 本机运行 Cue；先验证本机采集与打开，再验证一台 Linux SSH 远程来源。
- 会话发现、增量读取、已采集历史展示和来源身份。
- 事项聚合、队列排序、已读、已处理、延后和静音。
- 通知去重、刷新恢复、collector 重启恢复与采集状态展示。
- 按来源实际能力提供快捷打开，并明确打开的精度。
- 基于真实 session 的兼容性矩阵与回归样例。

### 条件性交付

普通消息发送只在完成开源实现审计和实测后启用；结构化审批另外验证，不能用普通文本发送能力代替。没有满足标准的实现时，首版只提供快捷打开，仍可发布。

### 后续候选

更多 harness 与 IDE 来源、多个远程主机、更完整的来源定位、稳定通道上的快捷回复、用户自定义排序规则。

### 暂不纳入

全功能 harness 托管、模型与认证管理、任意会话接管、自动派活、跨 agent 上下文迁移、修改原生历史、通用终端按键注入、团队云同步、完整 IDE 功能。

## 8. 技术方案

### 8.1 组件划分

```text
原终端 / IDE / harness
          │ 日志、原生事件、可选 hooks
          ▼
主机侧采集器 → 来源适配器 → 标准事件与会话索引
                                      │
                                      ▼
                           本地事项存储与队列引擎
                                      │
                                      ▼
                             Cue 卡片界面与通知
                                      │
                         快捷打开 / 可选投递器
                                      │
                                      ▼
                               原 session
```

采集与投递使用独立接口。某个来源只能读取，不需要实现一个假的完整运行接口。

候选技术组合为 TypeScript 主机服务、React 前端与 SQLite 本地存储。优先沿用团队熟悉的技术，具体选型在原型阶段确认；不因复用 UI 而自动继承 TopCard 的全部服务依赖。

### 8.2 会话与事项模型

- Session：内部 ID、host ID、harness、原生 session ID、项目、来源定位、能力、观察状态。
- AttentionItem：session ID、触发事件、原因、优先级、等待起点、处理状态与处理依据。
- SourceCursor：来源文件身份或原生游标、偏移、解析版本、最后成功采集位置。
- Delivery：客户端请求 ID、目标 session、消息内容引用、投递状态、确认依据与错误。

身份按主机、harness、原生会话组合确定，目录和显示名称不作为唯一身份。复制来的历史记录保留来源关系，不能因为路径相似就合并会话。

### 8.3 状态拆分

三个维度独立保存：

| 维度 | 示例 |
|---|---|
| 来源可观测性 | 在线、落后、离线、解析不支持 |
| 运行状态 | 运行、等待输入、空闲、结束、未知 |
| 人的处理状态 | 未读、待处理、延后、已处理 |

远程断线只改变来源可观测性，不自动判定 agent 已结束。来源端出现新用户输入时，可关闭该输入明确对应的等待事项；关联不确定时保留待办供用户判断。

### 8.4 增量读取与重放

文件监听结合补扫，处理半行写入、截断、重写和轮转。进度游标与事件入库在可恢复边界内提交，使用原生事件 ID 或确定性指纹去重。

历史导入与实时新事件走同一解析流程，但带不同处理模式。导入不批量制造通知；重放不重复创建事项。保存可选原始事件用于解析兼容性诊断，设置留存与清理边界。

### 8.5 远程采集

远端小型采集器只观察配置范围，通过 SSH 传递增量事件。断开后能从游标补齐；如远端产生速度可能超过保留窗口，需要本地缓冲与确认机制。

远程打开必须带主机与原生会话信息。支持时定位现有终端或既有入口；否则打开正确的远程目录并提供用户可执行的会话定位信息，不自动创建第二个同 ID 的活跃进程。

### 8.6 可选消息投递

优先使用已有维护与测试的原生接口或开源桥接实现。回复目标必须是确认后的原 session。

无法确认发送是否生效时显示结果不确定；没有端到端幂等保障，不自动重复投递。审批必须绑定具体待审批请求以及原生选项，不能把任意 `y` 当作批准。

## 9. 开源复用策略

| 来源 | 候选复用点 | 采用前的检查 |
|---|---|---|
| TopCard 当前代码 | 卡片队列、焦点保持、键盘交互、通知、消息展示 | 去掉对 Pi session 生命周期的直接依赖 |
| Codecast | session 发现、解析、来源定位和可选投递 | 模块可拆分程度、维护状态、实际支持版本、许可证与测试 |
| ACP 适配器 | 已经由可用 ACP 通道连接的 session 的交互 | 能否连接目标会话、输入所有权、恢复与审批语义 |

Codecast 和 ACP 是候选，不是已经选定的底座。读取能力不推出控制能力；ACP 适配器也不自动拥有任意外部已运行 CLI 会话的连接权。

发送实现准入标准：

1. 源码和许可证明确，能够按要求复用。
2. 有持续维护证据与当前版本兼容记录，不能只凭星数或 README 宣称。
3. 有目标会话识别、断线和进程退出处理。
4. 能区分已投递和不确定；明确说明重复发送风险。
5. 在选定的 harness、版本和终端环境中完成真实往返验证。

不满足标准时交付快捷打开；不启动自研通用输入注入器作为兜底。

## 10. 验收标准

以下是待验证的目标，不是已有性能结果。

| 场景 | 通过标准 |
|---|---|
| 两类真实 CLI 会话 | 能发现、显示新增正文、标识主机项目并打开支持的来源 |
| 本机实时性 | 在声明的测试环境中，从完整事件写入到卡片可见 P95 ≤ 2 秒 |
| SSH 实时性 | 在声明的网络条件下，同一指标 P95 ≤ 5 秒 |
| 并发与重启 | 10 个活跃 session 场景下，无交叉消息；重启补齐保留范围内事件 |
| 事件去重 | 固定回放样例重复播放后，不新增重复事项或通知 |
| 历史导入 | 旧消息可查看，不触发批量新消息通知 |
| 来源端处理 | 明确的新输入能消除其对应待办；不确定关联不误关闭 |
| 远程断线 | 显示离线或落后，不把 agent 假定为完成；重连可补齐 |
| 快捷打开 | 精确打开与降级打开标识正确，不误启动第二个活跃同会话进程 |
| 条件性回复 | 有稳定通道时往返成功，失败与不确定状态可见，无盲目重发 |
| 注意力体验 | 队列更新不抢正在输入的卡片；延后、处理、下一项行为稳定 |

用例至少覆盖等待回答、普通完成、工具报错、审批不可操作、流式半行、重复事件、原文件重写、进程退出与网络中断。

人工价值验证：选取同一组实际多会话任务，比较使用前后的发现延迟、完成单次处理耗时、漏看率和非必要窗口切换次数。先建立基线，再决定量化改善目标，不能将界面点击减少直接等同于任务效率提高。

## 11. 实施阶段与投入

估算假设：一名熟悉 TypeScript 和现有项目的工程师全职开发，使用 AI 辅助；包含基本真实场景验收，不包含全平台发布、云服务或任意 IDE 兼容。

| 阶段 | 产物 | 人日估算 |
|---|---|---:|
| P0：验证来源 | 两类 session 实际样本、兼容表、打开与发送候选审计 | 1–2 |
| P1：本机采集 | 发现、增量解析、索引、游标、历史导入 | 3–4 |
| P2：注意力闭环 | 卡片、事项、排序、处理、通知、快捷打开 | 3–4 |
| P3：稳定性验收 | 重启、重写、去重、来源端处理与十会话测试 | 2–3 |
| P4：首个远程来源 | SSH 采集、断线补齐、来源定位与实测 | 3–5 |

本机可试用版本约 9–13 人日；包含一个可靠远程来源的首版约 12–18 人日。范围比纯监测演示更完整，估算也包含恢复和验收成本。

快捷回复作为独立工作包：若已有合格实现，预留额外 2–4 人日接入一种受支持环境；若没有，结束该工作包，保留快捷打开，不影响首版完成。

先让一个 session 的“发现 → 入队 → 打开来源 → 在来源处理 → 队列同步”闭环成立，再扩大来源数量。未知格式或无法可靠定位的环境明确标注为暂不支持。

## 12. 主要风险与应对

- 历史格式变化：版本化解析器与真实样例回归；不支持时显式提示，避免静默漏收。
- 仅凭历史无法判断精确状态：记录证据来源，允许未知；优先采用可靠事件，减少启发式判断。
- 收件箱退化成噪声列表：按 session 聚合，历史不入新提醒，提供静音、延后与明确处理动作。
- 双入口产生重复操作：以事项和请求身份关联；有确认才关闭，有不确定性则提示。
- 开源投递能力不可拆分或维护不足：快捷打开就是正式降级路径，保持项目边界。
- 远程事件丢失：游标、补扫与缓冲；声明保留窗口，不承诺恢复源端已经删除的历史。
- 过度继承 TopCard：首版可以复制少量稳定 UI 模块并保留来源标记，验证共同需求后再提取共享库。

## 13. 立项决策

采用 Cue 作为独立项目名称，定位为 session 注意力队列。

优先完成本地与远程的可靠接收、事项处理和快捷打开。快捷回复以成熟开源能力的实际验证为前提，不作为扩大自研控制范围的理由。

首版成功的判断：用户能相信 Cue 告诉自己“现在该处理哪个会话”，并能快速到达真正可处理它的地方。
